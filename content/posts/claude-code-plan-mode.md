Claude Code を使い始めた頃は、いきなり「**○○を実装して**」と指示していました。すると Claude が走り出して、こちらが想定していない構造でファイルを作って、戻すのに時間がかかる、というパターンを何度も繰り返しました。

ある時、**Plan モード**の存在を知って試したら、上記の事故がほぼ消えました。今回はその Plan モードの使い分けをまとめます。

## Plan モードとは

Claude Code には「**Plan モード**」という動作モードがあります。通常モードと違って、Plan モード中の Claude は:

- **読み取り系のツールしか使えない**: Read / Grep / Glob / WebFetch などはOK
- **書き込み系は禁止**: Edit / Write / Bash の破壊的コマンドは実行できない
- **最後に「実装計画」をユーザーに提示**して承認を待つ

つまり、コードを書き出す前に「**こうしようと思います、いいですか？**」を取らせるモード。

## どう切り替えるか

通常モードと Plan モードの切り替えは、**`Shift + Tab` キー**を押すだけ。

- 1回押し: Plan モード ON
- もう1回押し: 通常モードに戻る

入力欄の周りに「PLAN」のような表示が出るので、いま自分がどっちのモードにいるかは見て分かります。

## どんな場面で効くか

私が Plan モードを使うと特に効く、と感じるのは以下のような場面です。

### 1. 新規ファイルを複数作る作業

「ブログに新記事を1本書く」「Hugo のテンプレートを新しく作る」など、**ゼロから複数ファイルを生成する**ような作業。Plan モードで、

- どのディレクトリに置くか
- ファイル名はどうするか
- frontmatter の項目構成は
- 既存ファイルとの被りはないか

までを先に固めてから実装に入ります。事故率が劇的に下がります。

### 2. 既存コードのリファクタリング

既存コードの構造を変える時は、Plan モードで:

- どのファイルを触るか
- どの関数を切り出すか
- テストはどう書き換えるか

を先に書き出させます。**触る範囲を可視化**してから着手することで、「あれ、ここまで壊すつもりじゃなかったのに」が防げます。

### 3. 仕様が曖昧なまま頼んでしまった時

「とりあえず○○できるようにして」のような曖昧な依頼を出してしまった時、Plan モードで一旦止めると、Claude が「**こう解釈しましたが合ってますか？**」と確認してくれます。

これがすごく効きます。曖昧な要件のまま走らせると、後でやり直しが発生しがち。

## 効かない・むしろ邪魔な場面

逆に Plan モードを使わない方がいい場面もあります。

### 1. 単純な1ファイルの修正

「この記事のタイポを直して」「設定値を1行変えて」のような**ピンポイントな修正**は、Plan モードを通すと冗長です。即実行が早い。

### 2. 探索・調査作業

「コードベースの中で `useState` を使っている箇所を全部探して」のような**読み取り中心のタスク**は、そもそも書き込みが発生しないので Plan モードを使う意味がありません。

### 3. CI で動かす自動処理

スクリプトとして自動実行する Claude Code 呼び出しでは、Plan モードに入ると承認が必要で止まってしまいます。CI 用途は通常モード一択。

## 「実装計画」が出たらどうするか

Plan モードで作業を依頼して、最後に Claude が**実装計画を提示**してきた時、選択肢は3つ。

### A. そのまま承認して実装に進む

提示された計画に問題なければ、承認ボタンを押す。Claude が通常モードに切り替わって実装を始めます。

### B. 計画を修正してもう一度

「**この章は要らない、こっちの章を足して**」のような追加指示を出すと、Plan モードのまま再計画してくれます。納得いくまで詰められる。

### C. 計画だけもらって、自分で実装

「**ありがとう、この計画を参考に自分でやってみる**」と返して終了。設計のセカンドオピニオンとして使うパターン。

## 実例: ブログ記事を書く時の使い方

私のブログ運用では、新記事を書く時はだいたいこの流れです。

1. 通常モードで「**○○について記事を書こうと思う**」と相談
2. Claude が候補トピックを3つくらい提示
3. 1つ選んで「**これでお願い**」
4. ここで **Shift + Tab で Plan モードに切り替え**
5. Claude が章立て・既存記事との被り検出・実コマンド構成を提示
6. 「これでOK」と返したら通常モードに戻って、実際にファイルを書き出す

Plan モードを挟まないと、いきなり長文を書き始めてしまい、後で章構成を変えたくなった時にゼロから書き直しになります。

## ハマりどころ

### 1. Plan モードのまま実装を頼むと止まる

「Plan モードのまま `Write` してくれ」は通らない。**承認を経て通常モードに戻ってから実装**、というフローを守る必要があります。

### 2. Shift+Tab を押したつもりが押せていない

入力欄に「PLAN」表示が出ているかは毎回確認したほうがいい。気付かず通常モードのまま頼んでしまうと、Plan モードのメリットが消えます。

### 3. 「とりあえず Plan モード」は時間の無駄

タイポ修正のような単純作業まで Plan モードを通すと、承認ステップが冗長です。**作業の大きさに応じて使い分ける**のがコツ。

## まとめ

- Plan モード = 読み取り専用で「実装計画」を出してくれるモード
- `Shift + Tab` で切り替え
- 効く場面: 新規ファイル複数作成 / リファクタ / 仕様が曖昧な時
- 効かない場面: 単純修正 / 探索 / CI 自動実行
- 承認後に通常モードに戻ってから実装が走る

Plan モードを覚えてから、Claude Code に対して**「言われたことを言われた通りに直す」回数**が劇的に減りました。コードを書く前に段取りを共有する、というのは人間同士でも変わらない仕事のコツです。

次回は、Plan モードと組み合わせて使う「**サブエージェントへの作業切り出し**」を書く予定です。
